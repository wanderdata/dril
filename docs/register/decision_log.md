# Decision log

Every framing, scope, data, definitional or implementation choice, numbered D-nnn. Entries are never deleted; superseded entries are marked as such, with a pointer to the entry that replaces them.

## D-001 (2026-11-18). One repository, shared core plus projects

The repository holds shared components in `dril/` and one folder per application in `projects/<name>/`. Reason: the four building blocks of DRIL (instrument, unit space, evidence policy, data-quality mechanisms) and the verification stage are common to all applications; writing them once keeps records comparable across projects and lets each project be audited with the same tools. The shared components will be written after the first projects specify their requirements, not before.

## D-002 (2026-11-18). Public repository

The repository is public, at the user's instruction.

## D-003 (2026-11-18). Copyrighted source documents are not committed

Papers and reports read for the project (for example NBER WP 35188) are listed in `references/literature_register.csv` with their URL, but the files themselves are not committed. ECLAC internal presentations and working documents are not committed unless the user says they can be published.

## D-004 (2026-11-18). Project layout

Each project folder holds `protocol/` (frozen protocols as delivered), `instrument/` (machine-readable instrument), `data/source/` (files as delivered, with hashes), `data/derived/` (tables built by script), `data/manual/` (hand-made tables, with their basis stated), `scripts/` (numbered pipeline) and `output/`. Projects are run by `run_all.py` at the root, which runs each script in a separate process, then `scripts/check_outputs.py`. The supplier-development application is `projects/proveedores`.

## D-005 (2026-11-18). Machine-readable instrument for proveedores Stage 2

`projects/proveedores/instrument/stage2_V260721.yaml` is generated by `scripts/00_instrument.py` from the variable dictionary delivered with the run (questions, types, codes and labels) and from protocol V260721 (blocks, statuses, citation contract, dependency rules). Six dependency rules come from the protocol's checklist (section 15, items 7–12); two more (`subsidio_cofinanciamiento = 2` implies `subsidio_cofinanciamiento_prop = -88`; `evaluacion_disponible = 2` implies `evaluacion_link = -88`) are stated only in the coding instructions of section 12 and are marked with source "12". `p_anio` and `subsidio_anio`, typed "Numérico" in the dictionary, are validated as years because the protocol asks for years.

## D-006 (2026-11-18). Entities in proveedores Stage 1: 1,102, not 1,208

The Stage 1 file has 1,208 rows but 1,102 distinct `entity_id`; the 106 extra rows are exact duplicates. Duplicates occur only for entities with `existe_programa_proveeduria = 1`, and no entity has more Stage 2 initiatives than Stage 1 rows, which is consistent with one row per Stage 1 candidate initiative (the Stage 1 output format, section 7 of V260714). We therefore count entities as distinct `entity_id` and candidates as rows of positive entities. This changes figures presented earlier (Wander and Carrillo, CEPAL presentation of 30 September 2026, slides 16–17; possibly CEPAL 2026c): entities searched 1,208 → 1,102 (national 327 → 251, subnational 881 → 851); "341 entities with at least one initiative" → 235 entities with at least one candidate, and 341 candidates. Found by checking the uniqueness of `entity_id` while inspecting the files. Reference values in `tests/reference_values.yaml`.

## D-007 (2026-11-18). Personal information removed before publication

The names of the external reviewers in the team's notes are replaced by "una revisora externa" and "tres revisores externos" (user's instruction). In two source workbooks the document metadata fields `dc:creator` and `cp:lastModifiedBy` held a personal name and an internal account name; they were blanked, leaving cell contents unchanged. Both hashes (as received and as committed) are recorded in `data/source/README.md`.

## D-008 (2026-11-18). Categorical values stored as codes in derived data

The compiled Stage 2 file stores categorical variables as labels ("Sin información", "Vigente"), and text and numeric variables with the codes -88 and -99. `data/derived/records.csv` converts labels to the codes defined in the instrument, so that every variable uses -88 and -99 consistently. Every stored value mapped to a code; the build stops if any value is neither a code nor a label.

## D-009 (2026-11-18). Source-type classification by domain

Evidence rows record the publisher but not a source role. To describe the source mix, domains matching a government pattern (gob, gov, gub, gouv, govt and similar second-level labels) are classed as government; the other 110 domains are classed by hand in `data/manual/source_domains.csv` from knowledge of the institutions (from memory, not checked against the sites). Para-statal bodies such as Sebrae and state development banks are counted as public agencies; state-owned firms (Petrobras, Codelco, BROU) separately. Twelve domains are left uncertain. The classification is descriptive and should be corrected where the user knows better.

## D-010 (2026-11-18). Diagnostics beyond the protocol's checklist (chosen after inspecting the data)

Added after looking at the evidence file, and labelled as such: (a) cells whose only evidence quotes are also cited for other initiatives, cross-tabulated by `nivel_programa` and status, to see whether parent-programme information used for editions is marked `proxy_used` as protocol section 13 requires; (b) quotes of three words or fewer; (c) share of evidence rows without source date; (d) budgets without currency. These are diagnostics for targeting verification, not error counts.

## D-011 (2026-11-18). Shared country table

`dril/countries.py` holds ISO 3166-1 alpha-3 codes, the Spanish names used in ECLAC files and UN M49 subregions (Caribbean; Central America including Mexico; South America) for the 33 ECLAC member countries in the region. All projects use it. Source spellings that differ (for example "Trinidad y Tobago") are mapped through an alias list.

## D-012 (2026-11-18). Continuous integration rebuilds outputs

The GitHub Actions workflow reruns every project pipeline from the committed source files and fails if any regenerated file differs from the committed one, then runs the tests. Committed outputs are therefore reproducible from source by construction.
